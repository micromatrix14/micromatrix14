The Bug-Fixing Agent

An AI teammate that turns a Jira key into a reviewed, buildable pull request — using our real requirements, our code, and our review discipline.

What it is

A Claude Code agent with a shared method + skills, per-repo memory, and live links to Jira / Bitbucket / JAMA / Figma.

Why

Consistent triage, honest verification, no silent guessing on safety-critical code. Sorts the backlog and fixes what's safely fixable.

Where it runs

In VS Code, on your machine, against your fork. Nothing merges without human review.

Generator repo cap_software_gui · TxM repo cap_software_rx_gui · Brain tool_dev_ai_hub
Honest scope

What it can and cannot do

Does well

  • Read a Jira ticket, all comments, and attachments (images, CAN/serial logs)
  • Pull the linked JAMA requirement and Figma mockup
  • View screenshots / mockups — see the real symptom and intended design
  • Decode CAN / serial traces against the protocol spec
  • Triage a bug and name the failure at file:line
  • Write the minimal fix, build, and run unit tests
  • Add a debug button that injects CAN messages to reproduce a bug on-device
  • Open a cross-fork PR with the ticket text + fix write-up; sort/label the whole backlog

Cannot / hands back

  • Cannot read video — needs key frames as screenshots
  • Cannot render QML — a UI/layout fix is reasoned, not seen; needs a human visual check
  • Cannot run on real hardware — bench/CAN verification is yours
  • Blocked bugs (missing asset, firmware-origin, needs a trace) → root-cause write-up, not a fake fix
  • Won't weaken a safety guard without sign-off
  • Never does the merge — the PR is a draft for review
How it works

The pipeline (Jira key → reviewed PR)

Three lanes out of triage: A confident fix → ship · B a proposed fix that still needs bench verification (shipped, but flagged) · C blocked → handed back with root cause, never a fake fix. Review today is you: ask it to explain the mechanism before it edits — the more you push on the "why", the more often a wrong guess is caught.

What each skill actually does — domains/sw/skills/

A skill is a written playbook for one bug shape: how to recognize it, where to look, how to prove the mechanism, and the fix pattern — each carrying the real tickets it was distilled from.

triage-bug
runs first, always		Before any edit: map the bug to the right repo (by which screen renders it, not which device the tester names), classify A desk-verifiable / B needs bench proof / C blocked, and pin the failure to a file:line. Stops confident-but-wrong fixes.every bug

Gen↔TxM		A value sent over CAN by one side and displayed by the other. Fixing only your side silently desyncs the other. Skills 2/4 · state & UI archetypes

Bug archetypes — state & QML

SkillSymptom → mechanism → fixReal tickets
missing-reset-on-event
usually A		"X stays after Y" / "settings kept in memory" / "stale value after returning". A member isn't cleared on a lifecycle event (generator/catheter disconnect, end-procedure, screen exit/entry) — or is cleared when it should persist. Fix = add or remove a reset in that event handler.FRP-5288 (banner reset on disconnect → remove), FRP-5299 (summary mode → add setTagMode), FRP-5351
qml-layout-overflow
B — needs a frame		"overlap / cut off / stranded / disappears on press / overflows". Purely visual — code can suggest a cause but can't confirm it. The recurring mistake is theorizing from code and fixing the wrong thing. Get the screenshot frame first, then confirm on-device.FRP-4164 (label overlap), FRP-5086, FRP-4816, FRP-5349
qml-lifecycle-trigger"X is already set even though I never opened that screen." One-time setup runs when QML constructs the component (app launch, every tab) instead of on navigation. Root cause: Component.onCompleted fires eagerly for all children of a StackLayout/StackView. Gate on the page actually becoming current.early-default / wrong-tab bugs
first-tick-enumeration-raceStatus briefly wrong right after connect/power-on/replug, then self-corrects a tick later — worse when many devices connect at once. The first poll reads an incomplete state and the code acts on it. Fix = wait for the settled enumeration before reacting.transient connect errors / flapping status
These are QML/Qt-generic — they'd apply to any Qt project, which is why FW/systems can reuse the same shapes.
Skills 3/4 · timing, static-analysis, assets

Bug archetypes — races & mechanical findings

SkillSymptom → mechanism → fixReal tickets
intermittent-timing
never ship as A		"sometimes / occasionally / seen 2 of 3 / black screen / crash", or a glitch only when two actions coincide. Reading code can suggest a cause but never confirm it — needs a trace/repro. The rule: do not present a guessed fix as confident, especially on a safety path.FRP-4653 (crash after many footswitch ablations), FRP-4955, FRP-3218, FRP-5131
thread-unsafe-singleton
Klocwork		Lazy if(!m_instance) m_instance=new T accessor — two threads both see null, both construct, one leaks and state splits. Mechanical fix to the well-known safe-init pattern.FRP-5408/5409 backlog
qsharedpointer-foreign-ownership
Klocwork		A QSharedPointer built from a raw pointer the code doesn't own (address of a reference, a singleton's resolve(), a member). Refcount hits zero → it deletes memory it never allocated → double-free/crash. Fix = don't take ownership (raw ref, or non-deleting deleter).FRP-5408 (&getHandler()), FRP-5411 (resolve())
asset-blocked
hands back		Looks like code but the fix is an artifact the agent can't author: text baked into an SVG as vector paths, a missing .wav, or a missing message-DB row showing as "Unknown Warning". Recognize fast, hand back exactly what's needed — no no-op "fix".FRP-5088 ("Software" in SVG), FRP-5147 (no beep .wav), FRP-4900 (DB seed)
Class shown as a chip where the skill forces it: intermittent = never confident-A; asset-blocked = always C.

How to write a skill

  • Front-matter name + description that says when to use it (the symptom wording the agent matches on)
  • Body follows the fixed shape: Recognize → Locate → Confirm mechanism → Fix pattern → Verify
  • Cross-link related skills with [[name]]

The one rule: shape, not specifics

  • ✅ Record the reusable pattern ("state that persists across an event is usually a missing reset in the handler")
  • ❌ Never bake in file:line, enum values, or test counts — they rot; the agent re-derives them from live code
  • Cite real FRP numbers only as brief "this happened" illustrations
FW & systems contribute the same way into domains/fw/ and domains/systems/ — never editing core/ or sw/. See CONTRIBUTING.md.

Setup — do this once

Point the agent at YOUR machine

Everyone's folders differ. The agent needs to know where your repos, reference docs, and screenshots live. Set these before first use.

1 · Install & connect

  • Clone tool_dev_ai_hub; run setup/Setup-Claude-Code.bat (installs Claude Code + Bedrock)
  • Fill your tokens in secrets/*.env (Jira / Bitbucket / JAMA / Figma) — your PAT + your BB_USER

2 · Repos — side by side

The domain profile expects the three repos in one parent folder. If yours live elsewhere, tell the agent your paths (or update domains/farastar/PROFILE.md):

<your-projects>/
  ├── cap_software_gui/
  ├── cap_software_rx_gui/
  └── tool_dev_ai_hub/

3 · Reference docs (CAN + error codes)

The agent reads the CAN protocol & error-code specs from your synced OneDrive — not the repo. Confirm they exist at your path:

C:\Users\<you>\OneDrive - Boston Scientific\Documents\
   FARASTAR CAN Protocol Architecture
   TxM Commercial Error Codes

Missing? Open each once from SharePoint so OneDrive syncs a local copy.

4 · Screenshots & logs

  • Ticket images: the agent downloads them itself
  • Your own captures / CAN logs: tell the agent the path (e.g. your …\Pictures\Screenshots) — there is no hardcoded location
If the agent can't find a repo, doc, or screenshot, it will say so — just give it the path. It never assumes a folder that isn't there.

Tips that make it work better

  • Give it the screenshot path for visual bugs — it can't read video, only image frames.
  • Point it at the CAN log for comm/timing bugs.
  • Ask it to explain the mechanism first if you want to sanity-check before it edits.
  • It will pause and ask when a decision is genuinely yours (requirement unclear, safety guard, risky action).
Golden path: a clear Jira key + any attached frames/logs → a reviewed AI-DRAFT PR you validate on the bench.

The pitch

What it does for you today

One AI teammate that takes a Jira key and does the whole loop — read, fix, build, test, PR — while you stay in control. Grouped by what it saves you:

Each card lists the built-in capability. Lines in mono are examples of what you'd type — plain English, nothing hard-coded; branch names, counts and dates are yours to change.

Fix a bug end-to-end

  • Runs the full loop from a ticket: branch off the current target branch, ask questions, commit, build, run tests, push the PR
  • Works across both Generator + TxM repos when a fix spans them
  • Squash / edit commits, add tests, cross-check build + test reports
  • e.g. "work on FRP-1234 on develop_commercial"

Understand the ticket

  • Reads the description, all comments, parses attachments, checks images
  • Video? Give it screenshot frames — it reads them from your capture folder
  • Reworks the fix when you point it at review comments
  • e.g. "read the comments and address them"

Work the backlog

  • Queries Jira and turns results into readable reports
  • Reads git history to spot likely duplicates — you set the range
  • Updates Jira fields — assignee, status
  • Creates PRs: copies the Jira description + adds a "Fix" section
  • e.g. "check last 2 months of commits — is this a dup?"

Report & share

  • Builds HTML status reports and presentations from a chat
  • Turns pasted Teams chat into a comment or a list
  • Chat transcript is a plain file — shareable, and it can scan another chat
  • e.g. "make an HTML status report from this"

You stay the reviewer

  • Make it explain the problem — you see if it truly understands
  • The more you challenge it, the more often a wrong fix gets caught
  • Sometimes it insists it's right — repeat the instruction
  • e.g. "explain the problem before you touch code"

The payoff

  • Backlog triaged and drafted fixes overnight
  • Consistent PRs the systems team can follow
  • Nothing merges without a human — it's a fast first draft, not autopilot
