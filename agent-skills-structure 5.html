The three layers

LayerScopeWhat lives there / why
core/ + agents/GENERICThe method (how to fix a bug trustworthily), the A/B/C triage classes, process guidelines, and the roles. Names no repo, holds no skills. Every discipline shares this untouched.
domains/<discipline>/SW FW/sysOne pack per discipline: a PROFILE.md (its repos, branch, build/test, subsystems, reference docs) + its own skills/. SW is filled in today; FW and systems are stubs in the same shape.
repo .claude/per repoMemory of one codebase: architecture maps, history, and the repo's CLAUDE.md build facts. Specific to that repo only.

Key idea: nothing product- or language-specific leaks up into core/. A skill that names Gen↔TxM or QML belongs in domains/sw/. When FW joins, they add domains/fw/ and reuse the same method & roles.

The 13 SW skills — what each is, and how specific it is

All 13 live in domains/sw/skills/, so all are "SW discipline". The right column says how portable the shape is: a FaraStar-specific skill encodes this product's structure (Gen↔TxM CAN, the therapy popup slot); a Qt/C++ generic-shape skill would help any Qt project and is the kind of thing FW/systems could adapt.

"Generic shape" skills sit in domains/sw/ today because SW is the only filled discipline. If a second Qt discipline appeared, the truly product-neutral ones (singleton, shared-pointer, layout, timing) are the candidates to generalize — but until then, one owner keeps it simple.

How FW & systems plug in

They never edit core/ or domains/sw/. Each adds its own pack in the identical shape:

domains/fw/
  PROFILE.md   # FW repos, integration branch, build/flash, subsystem map
  skills/      # FW archetypes (e.g. ISR timing, register-init order, CAN framing)
domains/systems/
  PROFILE.md   # systems repos/tools, requirement sources (JAMA), trace/report locations
  skills/      # systems archetypes (e.g. requirement-traceability, hazard review)

They inherit the shared method (core/AGENT.md), roles (agents/), and contribution rules (CONTRIBUTING.md) for free.

Reflects the real tree in tool_dev_ai_hub. Skill bodies follow a fixed shape: Recognize → Locate → Confirm mechanism → Fix pattern → Verify. Open in a browser, or Print → Save as PDF to share.
